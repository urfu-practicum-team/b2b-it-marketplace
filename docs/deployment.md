# Выкладка на стенд

Перед первой выкладкой с регистрацией создайте `$MARKETPLACE_SECRETS_DIR/marketplace_jwt_secret` со случайным ключом в Base64. Команда `openssl rand -base64 32` генерирует подходящий ключ. Ограничьте доступ к файлу так же, как для `marketplace_app_password`, чтобы его мог читать процесс Spring в контейнере. Оба экземпляра Spring используют один файл. Сохраняйте его между выкладками, чтобы подписи выданных JWT оставались действительными.

1. При push в `main` GitHub Actions собирает Docker-образ Spring и статику React из одного коммита. Полный SHA входит в тег образа и имена архивов. После обеих сборок Actions передаёт архивы по SSH.
2. На стенде `ci/receive.py` принимает два архива во временный каталог и запускает `ci/deploy.sh`. Скрипт берёт блокировку, чтобы выкладки шли по одной. Если на стенде уже более новый запуск, скрипт пропускает запоздавшую выкладку.
3. Скрипт загружает образ, распаковывает статику в каталог релиза и запускает свободный экземпляр Spring — `backend-blue` или `backend-green`. При старте Flyway применяет миграции к общей базе. Миграции должны быть совместимы с действующей версией Spring, которая в это время обслуживает запросы.
4. Скрипт опрашивает `/actuator/health/readiness` нового экземпляра из контейнера Nginx. Успешный ответ подтверждает готовность Spring и соединение с БД. При ошибке запуска или по тайм-ауту выкладка завершается с ошибкой. Пользователей продолжает обслуживать прежний релиз.
5. Для готового релиза скрипт записывает конфигурацию Nginx с новым адресом API и каталогом статики того же SHA. Он атомарно переключает ссылку `active.conf`, проверяет конфигурацию и отправляет Nginx команду reload. При ошибке проверки восстанавливает прежнюю ссылку. После завершения старых рабочих процессов Nginx скрипт останавливает предыдущий Spring.
