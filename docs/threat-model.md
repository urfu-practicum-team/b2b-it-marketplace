# Модель угроз и требования защиты данных

B2B-маркетплейс ИТ-услуг. Артефакт этапа проектирования, дополнение к матрице доступа.

Матрица задаёт права по роли, объекту и состоянию сделки. Параметры ограничений входа и сроки хранения предложены для согласования.

## Границы доверия и угрозы


| Объект | Кто или что создаёт угрозу | Возможный ущерб | Меры |
|---|---|---|---|
| Учётная запись | Посторонний подбирает пароль либо использует похищенную копию токена после выхода | Доступ к документам и действиям участника | З1–З2 |
| Документы верификации | Пользователь запрашивает чужой скан по идентификатору или прикладывает чужой файл к своей заявке | Раскрытие документа, верификация по чужим данным | З3–З5 |
| NDA и файлы сделки | Участник другой сделки получает чужой результат или подменяет вложение при сдаче | Утечка материалов, потеря достоверной версии результата | З3–З5 |
| Загружаемые файлы | Пользователь загружает опасное содержимое, файл с ложным типом или чрезмерного размера | Заражение устройства получателя, исчерпание хранилища | Приём потока, изоляция и проверка до выдачи, З4 |
| Платёжные webhook-и | Посторонний присылает ложное подтверждение, провайдер повторяет событие или доставляет его с опозданием | Преждевременная сдача работ, повторная выплата, неверный статус | Приём события и применение подтверждённого перехода, З7 |
| Хранилище, резервные копии и журнал | Избыточные права, сбой удаления, запись токена или скана в лог | Утечка после окончания срока хранения, невозможность установить автора действия | З5–З6 |

## Требования и критерии приёмки

### З1. Пароли и ограничения входа

Хранить только хэш Argon2id с индивидуальной случайной солью. Исключить пароль из журналов и ответов API. Для неверного пароля и неизвестного логина возвращать одинаковую ошибку. Предлагаемый лимит — 5 неудач за 15 минут по нормализованному логину и 30 за 15 минут по IP. При достижении любого лимита временно отклонять следующие попытки с кодом 429.

**Приёмка.** У двух пользователей с одинаковым паролем хэши различаются. Для шестой попытки по одному логину и для 31-й с одного IP по разным логинам срабатывают соответствующие ограничения. После истечения окна вход с верным паролем доступен.

### З2. Отзыв сессий

Срок действия access JWT — 15 минут с момента выдачи, refresh-токена — 7 суток. При обновлении сервер проверяет состояние сессии и учётной записи и атомарно заменяет использованный refresh-токен. При выходе сервер отзывает право текущей сессии на обновление, а клиент удаляет оба токена. Смена пароля и блокировка учётной записи отзывают право на обновление у всех её сессий. Ранее выданный access JWT действует до указанного в нём срока exp. Обычный запрос к API проходит проверку JWT без обращения к записи сессии.

**Приёмка.** После выхода refresh-токен этой сессии сразу получает 401, другая сессия продолжает обновляться. Сохранённый access JWT истекает в исходный срок, максимум через 15 минут после выхода.

**Изменение проекта.** В текущем OpenAPI выход описан как удаление токенов на клиенте. Для выполнения требования нужны операция серверного выхода, хранение состояния сессии и обновление описания авторизации.

### З3. Доступ к документам и результатам

При скачивании сервер проверяет право читать связанный объект по матрице доступа. При привязке файла к заявке, сообщению или результату сервер отдельно проверяет владельца загрузки, назначение файла, результат проверки содержимого и право изменить целевой объект. Доработку сохранять новой версией, сохраняя принятый результат и подписанный снимок NDA.

**Приёмка.** При подстановке чужого идентификатора сервер отклоняет скачивание и привязку закрытого файла с кодом 403 или 404. Содержимое и связи объектов сохраняются.

### З4. Проверка загрузок

Ограничить поток при чтении до 10 МБ. Применять список форматов по назначению. Для сканов разрешены JPEG, PNG и PDF. Для остальных назначений до реализации зафиксировать перечень поддерживаемых форматов. Сверять расширение, заявленный MIME и фактический формат по содержимому. Разрешать выдачу и привязку только после успешной антивирусной проверки, в том числе при повторной обработке после сбоя сканера.

**Приёмка.** Проверить корректный скан, превышение лимита, несовпадение типа, тестовый антивирусный образец и недоступность сканера. Только успешно проверенный файл можно привязать или скачать.

### З5. Хранение и удаление

Бакет закрыт, учётные данные доступны приложению. В PostgreSQL сохраняются метаданные, назначение и ключ объекта. Передача документов и резервных копий защищена шифрованием, доступ к копиям ограничен оператором восстановления. Для испытаний использовать только тестовые идентификационные документы.

| Данные | Предлагаемый срок и событие начала очистки |
|---|---|
| Незавершённые, отклонённые и непривязанные загрузки | Удалять через 24 часа с момента загрузки |
| Сканы верификации | Удалять через 30 дней после окончательного решения. До решения хранить для проверки заявки |
| NDA, результаты и вложения | Хранить до закрытия сделки или диалога и ещё 90 дней. При открытом споре отсчитывать срок после его закрытия и завершения сделки |
| Платёжные подтверждения и аудит | 180 дней после завершения операции или записи события. Хранить только поля, необходимые для сверки и расследования |
| Резервные копии | Ротация через 30 дней после создания. После восстановления перед открытием доступа повторно применить перечень удалений |

По истечении срока закрыть доступ и удалить содержимое и идентифицирующие метаданные. При сбое повторить удаление. Сроки согласовать до ввода в эксплуатацию.

**Приёмка.** На тестовых датах проверить истечение каждого срока, удержание материалов открытого спора, повтор после ошибки хранилища и восстановление резервной копии. Удалённый файл остаётся недоступным через API после восстановления.

### З6. Журналирование действий

Фиксировать успех и отказ входа, срабатывание лимита, выход и отзыв сессий, загрузку, привязку, чтение и удаление закрытых файлов, решения по верификации и спорам, административные изменения, приём и результат обработки webhook. Для события сохранять время UTC, идентификатор запроса, известного инициатора, действие, идентификатор объекта, результат и код причины. Для финансовых событий добавлять идентификаторы операции и провайдера. Исключить пароли, токены, секреты подписи, сканы, содержимое документов и полные тела платёжных запросов. Ограничить чтение журнала ответственными за аудит и защитить записи от изменения.

**Приёмка.** По идентификатору запроса восстановить, кто запросил закрытый документ и был ли выдан доступ. Проверить наличие события отказа, отсутствие секретов и запрет изменения записи обычным пользователем.

### З7. Подлинность и повторы платёжных webhook

Применять механизм конкретного провайдера. При наличии подписи проверять её по исходному сообщению и секрету по правилам провайдера. Если провайдер использует список IP, проверять источник по актуальному списку с учётом доверенных прокси. До изменения денег или статуса сделки запросить состояние операции у провайдера по аутентифицированному API. Сверить получателя, идентификатор операции, сумму, валюту и ожидаемый переход с локальной записью. При расхождении зафиксировать отказ. При временной недоступности провайдера оставить событие на повторную проверку.

Учитывать обработанные подтверждения. Повтор события не должен приводить к повторной финансовой операции, а запоздалое сообщение — к откату подтверждённого состояния.

**Приёмка.** Неподтверждённое уведомление сохраняет прежний статус сделки. Два подтверждения одной выплаты приводят к одной выплате.
