# Задачи итерации 2

Итерация «Основа платформы и инфраструктура» длится с 9 по 22 ноября 2026 года. По [плану развития проекта](<План развития проекта.docx>) команда разворачивает платформу, на которой участник может зарегистрироваться, найти исполнителя по квалификации и опубликовать задание.

По [паспорту проекта](<B2B-маркетплейс ИТ-услуг с верификацией и эскроу — паспорт.pdf>) фронтенд реализуется на React, серверная часть — на Java/Spring. [Описание компонентов](marketplace-design/components.md) определяет React SPA как пользовательский интерфейс платформы. Пользовательские экраны регистрации, профилей, портфолио, каталога и заданий в этой итерации подключаются к REST API. [Реестр требований с трассировкой](артефакты/Артефакт_2.1_Реестр_требований.md), включая DoR и DoD, закрыт в итерации 1 и входит в пакет КТ-2 как готовый артефакт 2.1. Карточки 17–21 охватывают артефакты 2.2–2.6 для всего проекта.

### 7. Настроить сборку, миграции и выкладку в GitHub Actions

**Заголовок:** Настроить сборку, миграции и выкладку в GitHub Actions

**Описание:** При каждом `push` в `main`, включая слияние PR, GitHub Actions автоматически выкладывает релиз на `https://it-pod.ru`. Пока новый экземпляр Spring запускается и применяет миграции, Nginx направляет пользователей на действующий экземпляр. Выкладки на стенд выполняются по одной.

1. **Собрать и доставить релиз.** Из одного коммита собрать Docker-образ Spring и архив содержимого `frontend/dist/`. Использовать полный SHA коммита в теге образа и имени архива статики. Только после обеих успешных сборок передать статику и сжатый образ (`docker save | gzip`) на VPS по SSH. Загрузить образ через `docker load`, а статику распаковать в отдельный каталог с именем по SHA. При таком способе доставки реестр образов не требуется.
2. **Запустить новый экземпляр.** Скрипт выкладки определяет по активной конфигурации Nginx, какой экземпляр обслуживает трафик, и запускает новый образ во втором. Имена в сети Compose — `backend-blue:8080` и `backend-green:8080`. Оба доступны Nginx по внутренней сети без публикации дополнительных портов на VPS. Они используют одну БД PostgreSQL, получают пароль приложения через Compose secret и монтируют общий каталог `/srv/b2b-it-marketplace/portfolio`. При старте нового экземпляра Flyway применяет миграции из карточки 4. Каждая миграция должна быть совместима с ещё работающей версией Spring.
3. **Дождаться готовности.** Подключить Spring Boot Actuator и включить `readinessState` и `db` в группу `readiness`. Из сети Compose опрашивать новый экземпляр напрямую, например `http://backend-green:8080/actuator/health/readiness`. Ответ `200 OK` означает, что Spring завершил запуск после миграций и индикатор `db` подтвердил соединение с PostgreSQL через DataSource приложения. При ошибке запуска или истечении тайм-аута завершить workflow с ошибкой. Действующий маршрут и опубликованная статика в этот момент по-прежнему обслуживают пользователей.
4. **Переключить API и страницу вместе.** Для релиза подготовить конфигурацию Nginx, в которой `/api/` проксируется на готовый экземпляр, а `root` указывает на статику того же SHA. Смонтировать в Nginx каталог конфигураций и каталог релизов. Атомарно переключить симлинк `active.conf` на конфигурацию релиза и выполнить `nginx -t`. При ошибке проверки восстановить прежний симлинк и завершить workflow с ошибкой. При успехе выполнить `nginx -s reload`: новые соединения принимает новая версия конфигурации. Остановить прежний Spring после того, как старые рабочие процессы Nginx завершат обслуживание принятых соединений.

**Критерий готовности:** На тестовом стенде проверить успешную выкладку и отказ. При успешной выкладке запросы к API по HTTPS проходят во время смены экземпляров, страница новой версии получает ответ от API, предыдущий экземпляр остановлен. При ошибке миграции или проверки готовности workflow завершается с ошибкой, прежняя страница и API продолжают отвечать. Повторная выкладка сохраняет тестовую запись в БД и ранее загруженный файл портфолио.

**Назначить на:** Не выбрано. Рекомендуемая роль — инженер инфраструктуры.

**Срок выполнения:** 22.11.2026.

**Зависимости:** 1, 3, 4, 5, 6.

### 22. Настроить обязательные проверки pull request в GitHub Actions

**Заголовок:** Настроить обязательные проверки pull request в GitHub Actions

**Описание:** При открытии PR в `main` и каждом обновлении его кода запускать сборку и тесты Spring через `mvn verify`. Для React запускать ESLint с правилами React Hooks, тесты Vitest и сборку Vite. Первые тесты привязать к продуктовому сценарию, например к регистрации из карточки 8. Стартовая страница с индикатором `UP` остаётся заглушкой.

Собирать отчёты о покрытии строк через JaCoCo для Java и Vitest для React. Учитывать все исходники приложения, включая файлы без тестов. Разделить сумму покрытых исполняемых строк обеих частей на общее число исполняемых строк.

В правилах слияния в `main` сделать обязательной проверку с постоянным именем `coverage-gate`. Через `$GITHUB_STEP_SUMMARY` публиковать в сводке запуска Markdown-таблицу с тремя строками — «Фронтенд», «Бэкенд» и «Итого». Для каждой строки указывать число покрытых и общее число исполняемых строк, а также процент покрытия. Публиковать таблицу и при результате ниже порога.

**Критерий готовности:** Для актуального коммита PR видны результаты линтера, сборок и тестов. Из проверки `coverage-gate` можно открыть сводку с таблицей покрытия. При суммарном покрытии ниже 70% проверка завершается ошибкой и блокирует слияние. При покрытии от 70% включительно и успешных остальных проверках CI разрешает слияние. Проверки работают без секретов стенда.

**Назначить на:** Не выбрано. Рекомендуемая роль — инженер инфраструктуры.

**Зависимости:** 1. Первый продуктовый сценарий для тестов согласовать с исполнителем карточки 8.
